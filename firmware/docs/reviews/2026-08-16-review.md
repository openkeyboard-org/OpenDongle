The main conclusion is that AES-CCM itself appears correct. The encrypted build failures are primarily caused by broken capability/key lifecycle, unsafe build profiles, and likely radio/AES concurrency—not an endian, nonce, AAD, or tag-format mismatch.

Scope covered all first-party OpenDongle firmware, platform code, build/release tooling, Rust/Python utilities, tests, documentation, OpenBoot boundaries, and the relevant OpenController protocol interactions. No hardware operations or tracked source-file edits were performed as part of the review.

## P0 — Release blockers and critical defects

### 1. Confirmed: the default CH592 “product” build is actually a bench-encryption image

The ordinary product target enables a compiled-in static AES key, forced encryption, previous-session diagnostics, and UART telemetry. The release machinery accepts and packages this configuration without a guard.

Besides exposing a shared test key, forced encryption can break an existing plaintext bond after reboot because the dongle starts rejecting plaintext HID as a downgrade.

Evidence:

- [`firmware/ch592/src/dongle_target.h:64`](firmware/ch592/src/dongle_target.h#L64)
- [`firmware/common/src/rf_task.c:3388`](firmware/common/src/rf_task.c#L3388)
- [`firmware/ch592/Makefile:182`](firmware/ch592/Makefile#L182)

### 2. Confirmed, likely direct cause of encrypted mode failure: provisioning does not update the dongle’s live crypto state

`BondWrite` validates and persists the new record but does not install the key or encryption latch into the running RF task. Runtime installation only occurs during boot.

OpenController’s bench provisioning activates its key immediately. Consequently, after provisioning, the controller may require encryption while the still-running dongle remains plaintext. A dongle reset currently acts as an undocumented required step.

Persistence success is also reported without checking the flash-write result or reading the saved record back.

Evidence:

- [`firmware/common/src/iap.c:194`](firmware/common/src/iap.c#L194)
- [`firmware/common/src/rf_task.c:3387`](firmware/common/src/rf_task.c#L3387)
- [`firmware/common/src/bond.c:101`](firmware/common/src/bond.c#L101)

### 3. Confirmed, likely direct cause: capability negotiation is lost during normal pairing

OpenController sends capability frames before its first pairing beacon. OpenDongle records that capability, then clears it when accepting the fresh beacon. The resulting bond is therefore normally recorded as encryption-incapable.

The bench provisioning utility masks this defect by force-setting both encryption flags.

Evidence:

- [`firmware/common/src/rf_task.c:1675`](firmware/common/src/rf_task.c#L1675)
- [`../OpenController/firmware/src/rf_task.c:1338`](../OpenController/firmware/src/rf_task.c#L1338)

### 4. Confirmed: the current CH570 production firmware does not link

Static data leaves 1,800 bytes of stack space, below the enforced 2,048-byte floor. This prevents CH570 application, factory, bundle, and top-level release builds from completing.

Evidence:

- [`firmware/ch570/link.ld:201`](firmware/ch570/link.ld#L201)
- `firmware/ch570/build/ch570-product-slotA/opendongle-ch570-product.map`, around lines 1344–1358

## P1 — High-priority correctness and security defects

### 5. Known, confirmed: CH570 truncates long scheduler deadlines to 26 bits

EV10 schedules 212,500,000 ticks, but the timer register holds only 26 bits. It fires after roughly 112 ms instead of 2.125 seconds while the software epoch advances by the untruncated interval. This distorts RF timing and supervision.

Evidence:

- [`firmware/ch570/src/main.c:318`](firmware/ch570/src/main.c#L318)
- [`firmware/common/src/rf_task.c:1207`](firmware/common/src/rf_task.c#L1207)

### 6. Newly identified, confirmed: CH570 collapses all HID traffic into one newest-wins slot

Keyboard, mouse, and consumer reports share a single deferred buffer. A second RF report can overwrite the first before the foreground pump runs.

This policy is invalid for relative mouse deltas and for press/release transitions. Cross-report overwrite can discard a keyboard release and produce a stuck key. Remote-wake handling supplies a concrete multi-millisecond window where this can occur.

Evidence:

- [`firmware/ch570/src/main.c:74`](firmware/ch570/src/main.c#L74)
- [`firmware/ch570/src/main.c:111`](firmware/ch570/src/main.c#L111)
- [`firmware/ch570/src/main.c:760`](firmware/ch570/src/main.c#L760)

### 7. Newly identified, confirmed: the updater prints the wrong artifact for A/B flashing

The Rust CLI accepts a family-guard `.bin`, then tells the operator to flash that same path. A/B updating requires the `.obb` bundle; a raw `.bin` is treated as slot A and normally fails when slot B is the write target.

Evidence:

- [`tools/src/main.rs:157`](tools/src/main.rs#L157)
- [`tools/src/main.rs:361`](tools/src/main.rs#L361)
- [`tools/src/hex.rs:288`](tools/src/hex.rs#L288)
- [`firmware/BOOT.md:89`](firmware/BOOT.md#L89)

### 8. Known, confirmed: EP6 can be permanently NAKed by an unaccepted OUT packet

The ISR NAKs EP6 even when toggle validation or an already-pending packet prevents it from latching the new command. Only successfully processed pending work re-enables the endpoint, so duplicate-toggle or pipelined traffic can wedge IAP until reset or replug.

Evidence:

- [`firmware/common/src/usb_device.c:607`](firmware/common/src/usb_device.c#L607)
- [`firmware/common/src/usb_device.c:971`](firmware/common/src/usb_device.c#L971)

### 9. Known, confirmed: suspend handling can replay stale mouse or consumer input

Suspend NAKs only the keyboard endpoint. A queued mouse or consumer press can remain armed while its release is discarded, then be transmitted after resume.

Evidence:

- [`firmware/common/src/usb_device.c:510`](firmware/common/src/usb_device.c#L510)

### 10. Confirmed: the advertised AES cross-build validation is broken for all six configurations

CH570 validation includes `dongle_target.h` without defining its clock dependency. CH592 does not put its target header on the include path. As a result, none of the hardware AES/CCM validation images currently compile.

Evidence:

- [`firmware/validation/Makefile:92`](firmware/validation/Makefile#L92)

### 11. Confirmed security limitation: plaintext HID and pairing confirmation are not authenticated

In plaintext mode, access address and CRC provide error detection but no peer authentication. A nearby transmitter that learns the RF parameters can inject shape-valid HID frames. Similar unauthenticated frames can confirm a tentative pairing candidate.

Encryption only protects keyboard-to-dongle HID; pairing, polling, and LED traffic remain outside that authenticated channel.

Evidence:

- [`firmware/common/include/rf_protocol.h:247`](firmware/common/include/rf_protocol.h#L247)

### 12. High-risk hypothesis: CH592 radio/AES overlap may cause intermittent MAC failures

AES and radio functions share a peripheral/register cluster. Crypto sealing can begin while an asynchronous RF transmission is still active, and vendor encryption code explicitly clears PHY state before using AES.

Existing host vectors cannot exercise this contention. The observed intermittent MAC-failure pattern is consistent with it, but silicon instrumentation or an A/B build deferring AES until `TX_FINISH` is required to confirm it.

Evidence:

- [`firmware/ch592/src/hal_aes_ch592.c:16`](firmware/ch592/src/hal_aes_ch592.c#L16)

## P2 — Important robustness and release-assurance issues

### 13. Newly identified, confirmed: USB reset does not cancel deferred IAP state

Bus reset neither clears a pending EP6 command nor disarms the IAP mutation session. Because reset re-enables EP6, a new packet may overwrite the shared DMA buffer while foreground code still holds the previous length.

Evidence:

- [`firmware/common/src/usb_device.c:489`](firmware/common/src/usb_device.c#L489)

### 14. Known, confirmed: hop-repeat correction mishandles some missed-slot intervals

When the elapsed interval is a nonzero multiple of five, the correction can move the anchor into the future and later overflow. The link eventually recovers through supervision, but experiences avoidable desynchronization.

Evidence:

- [`firmware/common/include/rf_protocol.h:316`](firmware/common/include/rf_protocol.h#L316)

Missing all eight announcements forces supervision/reconnect recovery. The 64-frame unauthenticated silence guard prevents permanent failure, but the design remains fragile and produces avoidable connection churn.

### 18. Hardware-dependent risk: CH592 has only 1,824 bytes of true stack

The fixed BLE arena constrains the stack, while the custom baseband trampoline consumes 128 bytes before entering opaque vendor code. There is no stack watermark or worst-case RF/USB/AES interrupt-depth measurement.

### 19. Hardware ABI risk: both startup and interrupt paths are brittle vendor seams

CH570 combines vendor startup code with a strong custom reset handler that installs temporary RAM vectors, copies high-code sections, and changes execution-mode CSRs. CH592 forks the full startup/vector implementation and adds a custom BB interrupt trampoline because the stock scheduler omits that handler.

Layout assertions help, but no automated disassembly/vector contract test or full reset/interrupt silicon matrix protects these assumptions across SDK and toolchain changes.

Evidence:

Update records use CRC rather than authenticity. Wrong-family protection is host-side and can be bypassed through raw OBP. There is also no unified manifest chaining the bootloader, slot A, slot B, bundle, and final factory image hashes.

Interrupted-update hardware validation is complete for neither all paths nor both chips; CH592 has substantially less hardware A/B evidence than CH570.

## Encryption-specific assessment

The AES-128-CCM construction matches across the two implementations and their host references:

- eight-byte authentication tag;
- two-byte CCM length field;
- thirteen-byte nonce;
- matching session-ID, direction, and counter byte order;
- matching AAD fields;
- matching encrypted packet lengths.

Host vector and reference tests pass. No deterministic cryptographic-format mismatch was found.

The most likely reasons the encrypted version fails are therefore, in order:

1. The capability advertisement is cleared during pairing.
2. Dongle provisioning updates flash but not the running crypto state.
3. The controller changes its runtime key state immediately, producing a live-state mismatch until the dongle reboots.
4. The default CH592 product profile force-enables a bench key rather than representing a clean production configuration.
5. The production system has no completed key-establishment lifecycle beyond bench provisioning.
6. Remaining intermittent authentication failures may come from overlapping RF and hardware-AES activity.

## Major test-coverage gaps

There is no direct executable coverage of:

- complete RF state-machine and event interleavings;
- capability negotiation through pairing and reconnect;
- live provisioning state transitions and flash readback;
- session-announcement loss and recovery;
- hop and supervision boundary cases;
- integrated radio and hardware-AES concurrency;
- CH570 mixed HID handoff and relative-mouse accumulation;
- USB toggle errors, pipelined EP6 traffic, bus-reset cancellation, and IAP arming lifetime;
- suspend/resume behavior for every HID endpoint;
- runtime stack high-water marks;
- interrupted updates across every chip and transport;
- adversarial plaintext frame injection and tentative-pair authorization.

## Recommended repair order

1. Split bench and production CH592 profiles and make release builds reject static keys and diagnostic flags.
2. Repair capability negotiation and make `BondWrite` atomically persist, verify, and activate the live key.
3. Define and implement the production key-establishment and rekey lifecycle.
4. Fix CH570 RAM usage and the 26-bit timer scheduler.
5. Correct the updater’s `.bin`/`.obb` contract.
6. Fix the CH570 HID queue and USB endpoint/reset state machines.
7. Restore all AES cross-builds and make full dual-chip release construction a mandatory CI gate.
8. Add a unified release manifest covering bootloader, both slots, bundle, and factory image.
9. Run radio/AES concurrency, stack-watermark, suspend/resume, interrupted-update, and adversarial RF tests on hardware.
